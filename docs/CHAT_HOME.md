# Діалогова головна бібліотеки

Статус: реалізовано; offline Go/browser acceptance пройшло. Цей документ
конкретизує REQUIREMENTS/HLD; джерела рішень — поточні вказівки користувача.

## Продуктова поведінка

Головна — діалог з бібліотекою. Над чатом компактні категорії з кількістю
матеріалів; справа теги, вибрані виділені, є пошук/розгортання словника.
Кількості глобальні для бібліотеки; показуються до200 категорій/тегів.
Мобільний екран складає панелі без горизонтального прокручування. Нижнє
поле повідомлення спільне для неформального тексту, одного URL та пачки.
Історія має власну область прокручування; поле введення залишається
видимим унизу екрана. Після Enter або кнопки відповідь показується від
початку, без стрибка до кінця довгої добірки. На низькому мобільному
екрані панель тегів прихована, щоб залишити місце для відповіді. Окремих режимів
одиночного/пакетного додавання немає. Постійний список
статей під чатом прибирається; картки з’являються тільки як результат дії.

Чат підтримує додавання статей/YouTube, поступове читання непрочитаних
вхідних, повтор невдалих дайджестів, дообробку старих статей, пошук і
уточнення пошуку, категорії/теги, пояснення пошуку за змістом та керування
його індексом. На картках доступні відкриття, збереження/відкладання,
read/unread і явна користувацька оцінка. Повні картки й спеціалізовані
сторінки залишаються доступні за прямими посиланнями; старий пошуковий
екран переноситься на /browse для сумісності й діагностики.

Повідомлення тільки з URL або явне «додай» із URL розбирається без моделі:
пробіли/переноси рядків, статті/YouTube разом, до500 URL/64KiB. Canonical
dedup і рядкові результати працюють як раніше; відповіді містять фактичні
added/existing/failed counts та посилання. Жодного inference для bare URLs
або відсіяних під час такого додавання джерел.

## Діалог і уточнення

Зберігаються історія, активні критерії, останні показані картки, позиція
«наступних п’яти» та очікуване уточнення. «Тільки SQLite» доповнює поточний
пошук, «прибери тег» знімає умову, «скинь пошук» починає новий. Пошук
охоплює тему/режим, category/tags, placement/read/state/filter, користувацьку
оцінку, model confidence та сортування; додаткові критерії можуть бути
описані природною мовою. Власна оцінка і confidence моделі не змішуються.

Відсутнє обов’язкове поле або неоднозначна дія спричиняє одне конкретне
запитання з можливими відповідями. Наприклад «перезапусти» → дайджести чи
дообробка; «додай тег» без контексту → до пошуку чи до матеріалу; «додай
статтю» без URL → посилання. Відомі параметри не перепитуються. «Друга»
посилається тільки на останню явно показану добірку, не на довільний DB ID.
Зміна пошуку скидає його сторінку. Новий діалог очищає лише стан чату.

Пошук за змістом пояснюється як пошук близьких ідей без точного збігу слів.
Типовий тематичний запит використовує hybrid; якщо індекс недоступний,
виконується FTS із явним повідомленням. URL/кнопки/очевидні команди та
поточний стан черги працюють без генеративної моделі.

## Зрозумілі відповіді й пояснення відмов

Чат може відповідати звичайною українською мовою: пояснювати роботу
бібліотеки, підтримувати коротку розмову й відповідати на уточнення.
Для цього є окремий read-only намір answer; він не виконує операцій і
не скидає очікуване уточнення. Відомості про фактичний стан та причини
відмов формує сервер із поточної бази, а не модель із давньої історії.
Запитання «чому аналіз залишається незавершеним?» запускає діагностику,
не повтор обробки. Відповідь відрізняє чергу, виконання й невдалі спроби,
пояснює тип відмови та радить наступний крок. Постановка в чергу не
описується як завершення обробки.

Одна повна Markdown-обгортка з позначкою `json` навколо аналізу допускається.
Після зняття обгортки зберігається сувора перевірка схеми та змісту;
зайві поля, текст зовні, кілька відповідей і неповний JSON відхиляються.
Попередні діагностичні файли не змінюються, масовий повтор не запускається
без явного запиту користувача.

## Виконання і джерело правди

Cloud Gemma 4 31B через локальний Ollama — первісна модель діалогу; окрема
настройка chat model/timeout у .env. Локальна генерація виключена. Модель
повертає дозволений структурований намір/параметри/уточнення або текст
звичайної відповіді для answer;
сервер перевіряє їх і викликає наявні операції. Модель не генерує SQL,
не отримує довільного доступу до DB/файлів і не вигадує counts або статус
«виконано». Джерела/назви/метадані в контексті — дані, не команди.

Помилки моделі не гублять повідомлення або URL; чат показує пояснення й
доступні прямі дії. Довга дія має видимий індикатор виконання. Історія і
стан переживають перезапуск, входять у DB backup; GET не виконує дій і
не позначає прочитаним. Session cookie HttpOnly/SameSite, POST захищений
Host/Origin/CSRF, агентські credentials не дають права запису.

Ідентифікатор повідомлення запобігає повторному виконанню після double-click/
повторного POST. Повтор прийнятого повідомлення повертає збережений результат.
Незавершена під час збою мутація не повторюється тихо; її невизначений стан
пояснюється, фактичну чергу/картку можна прочитати. Knowledge batches
використовують durable receipts, digest retries — точні source/job/attempt
references; completed/active work і checkpoint policy збережені. Явна
оцінка користувача обов’язкова для rating; модель не вибирає значення.

## Приймання

1. Порожня головна містить чат/категорії/теги, без URL/search forms та
   автоматичного списку статей. Desktop/mobile keyboard navigation працює.
   Enter у довгому діалозі залишає поле введення, індикатор виконання й початок нової відповіді видимими.
2. Один URL/пачка з пробілами чи переносами приймаються з одного поля без
   виклику моделі; повтор повідомлення не створює нової обробки.
3. Неформальний запит → структурований пошук → п’ять карток; уточнення й
   кліки category/tag зберігають решту критеріїв. Наступні картки не губляться.
4. Уточнення потрібне лише за відсутніх/неоднозначних параметрів; коротка
   відповідь продовжує попередню дію. Відновлення чату після restart.
5. Перезапуск/дообробка з чату показує фактичні результати й не починає
   completed work заново. Queue status і index actions доступні в діалозі.
6. Item actions прив’язані до показаних джерел; людська rating history
   зберігається; GET/модель без явної оцінки її не змінює.
7. Denied origins/CSRF/agent writes, unknown model actions/параметри,
   malicious retrieved text, stale/concurrent/replayed turns — без зайвих
   мутацій. Fake-cloud browser/Go acceptance; live model tests окремо.


Реалізація: schema_v13.sql, chat_store.go, chat_plan.go, chat_control.go,
chat_web.go, chat.html/chat.js. Історія на екрані обмежена останніми30
повідомленнями (повна історія залишається в DB); для поступового перегляду
зберігаються до1000 посилань результатів. Пакетний повтор перевіряє до5000
відмов за натискання й ставить у чергу до500; більші вибірки можна уточнити
або переглянути на спеціалізованій сторінці. Один незавершений запит
блокує інші POST чату цього процесу, але не GET/роботу фонової черги.

Go acceptance: chat_test.go — persistent replay/restart/paused restore,
URL/no planner, criteria/facets/paging, rating provenance та явне число
(номер картки, від’ємні й дробові числа не стають оцінками), untrusted
planner data/unknown actions/cloud-only, busy/stale/interrupted, typed
retries/progress і HTTP boundaries. Config acceptance: config_test.go.
Browser: smoke_chat_ui.py — unified input, natural intent через fake cloud,
FTS fallback/refinement, five-at-a-time, explicit rating/clarification,
queue/history/new dialogue, escaped text та desktop/mobile viewport.
Live Gemma quality/latency не вимірювалися цими перевірками.

## Жива перевірка діалогу

Наступна integration перевірка — українські запити до налаштованої cloud
Gemma через локальний Ollama. Окремий fixture store у ./tmp/, лише
синтетичні статті/теги; workers paused, embeddings/Telegram disabled.
Немає запису в реальну бібліотеку, читання особистого корпусу або локальної
генерації. Пошук/refinement, теги, явні дії/оцінка, коротка відповідь на
уточнення й неоднозначний повтор перевіряються через справжній chat POST.
Записуються actual cloud alias, намір/результат та тривалість кожного ходу.
Це вибіркова перевірка інтеграції/розуміння намірів, не бенчмарк якості
semantic retrieval чи особистих рекомендацій. Live helper
minions/live_chat_smoke.py потребує явного --run-cloud й не входить у make check.

Виявлений live випадок: Gemma повернула текстове clarify для «Оціни перший
матеріал», а після «3» повторила його. Для вже відомої дії/картки pending
має зберігати typed item command, а не лише текст запитання. Для item action
модель передає відомі item_action/index; missing score/index уточнює сервер.
Якщо cloud повертає generic clarify для явного rating request з номером чи
порядковим словом, сервер зберігає цей безпечний слот сам. Значення власної
оцінки все одно вводить користувач; номер картки не стає оцінкою.


Живу перевірку виконано 2026-10-12: 13/13 ходів пройшли після виправлення,
10 cloud запитів; `gemma4:cloud`, remote model `gemma4:31b` на ollama.com,
actual reply model `gemma4`. Український пошук/refinement, додати/прибрати тег,
збереження другої картки, explicit rating/short answer, read, ambiguous retry,
short retry-kind answer, knowledge batch та пошук за власною оцінкою.
Число оцінки, retry-kind і пачка URL завершуються без cloud inference.
У кількох малих fixture запусках ходи з моделлю займали приблизно0.4–1.6s;
це спостереження для синтетичного малого контексту, не обіцянка production
latency. Workers paused, semantic retrieval disabled (перевірено FTS fallback),
немає ready digest candidates: пакетні наміри перевірені з фактичним нульовим
результатом, pipeline/progress перевірені окремими offline tests.
Перевірка не записувала в реальну DB/оцінки й не надсилала Telegram. Повні локальні reports у ./tmp/.
Offline tests також перевіряють explicit opt-in, loopback-only forwarding,
cloud identity, відсутність auth у звіті та облік невдалого запиту без повтору.

Раніше збережене generic rating question також відновлює відому дію/картку
для короткої числової відповіді без повторного planner call (Go regression).
