# Рев'ю та захист main

## Стан

Користувач погодив: рев'ю виконує агент, після затвердження агент також
виконує злиття. Повторного дозволу користувача на злиття перевіреного PR
у межах дорученої роботи не потрібно.

Перевірено 2026-10-10: активний ruleset
[`prs`](https://github.com/valpere/news-library/rules/24834135) для default
branch `main` вимагає PR, забороняє видалення та force-push. Винятків для
обходу немає. Required approvals = 0; обов'язковий status check — `news-library-check`, strict; resolution увімкнено.
Workflow `.github/workflows/ci.yml` і шаблон PR опубліковані через PR #1.

## Робочий цикл

Зміни робити в окремій гілці, наприклад `feat/m1-ingestion`. Перед зміною
гілки перевірити незакомічені файли; не переносити сторонні зміни в PR.
У PR описати результат, перевірки й відповідний пункт вимог. Після рев'ю
виправити підтверджені проблеми та повторити перевірки для фінального коміту.

Для Codex прочитати `~/wrk/common_codex/skills/fix-review/SKILL.md`.
Приклад запиту: «Застосуй fix-review до PR №N; перевір зауваження,
виправ підтверджені проблеми й після затвердження злий перевірений PR».
Це локальна інструкція агенту, а не встановлений GitHub-бот.

Початково достатньо одного окремого проходу рев'ю агентом із перевіркою
коду, вимог і тестів. Для суттєвих змін сховища, черги, доступу або
інтеграцій доречний окремо обраний консиліум cloud-моделей. Арбітр
перевіряє кожне зауваження за доказами; голосування не визначає істину.
Збій рецензента означає неповне рев'ю. Зміна коду після перевірки потребує
оновлення звіту. Позитивний висновок агента `ready` означає затвердження
в цьому процесі; він не видається за GitHub Approve від іншого акаунта.

## Злиття агентом

Агент завершує доручену роботу через PR, публікує підсумок рев'ю та зливає
його без окремого запиту дозволу, коли одночасно виконано такі умови:

- Рев'ю завершено, підтверджені дефекти усунено, немає невирішених
  блокувальних питань; результат `ready` стосується фінальних head і base SHA.
- Відповідні локальні перевірки пройшли. Якщо CI вже налаштовано, його
  перевірки також завершилися успішно, навіть якщо ruleset ще не вимагає їх.
- Віддалений PR містить саме перевірений коміт, немає конфліктів,
  невирішених зауважень або незадоволених вимог GitHub.

Перед злиттям повторно звірити head/base та результати перевірок. Для
захисту від нового push між перевіркою й злиттям передати перевірений SHA:

```bash
gh pr merge <PR-number> --repo valpere/news-library --squash --match-head-commit <reviewed-head-sha>
```

`--admin` та послаблення захисту не використовувати. Якщо код або база
змінилися, оновити рев'ю й перевірки; якщо вони не завершені чи неуспішні,
залишити PR відкритим із причиною. Після команди перевірити стан PR на
GitHub і повідомити посилання та merge commit; очікування в черзі не є
завершеним злиттям. Видалення гілки не входить у цю команду.

## CI

Check `news-library-check` запускає `make check` у Python 3.12 на PR до
`main` і після злиття. Він збирає Go-застосунок, запускає acceptance tests з race detector та vet,
перевіряє трасування актуальних вимог через
зафіксований `tumanomir`, документи, синтаксис Python і наявні результати
пілотів; моделі не викликаються, секрети не потрібні. Збирання приладу
перед перевіркою потребує Go й завантаження залежностей.
Go build/test входять у `make check`; ім’я обов’язкового check збережено.

## Підключення CI до захисту

Спершу опублікувати погоджений склад підготовки в окремій гілці й відкрити
PR із workflow. Репозиторій публічний: локальні тексти та особисті оцінки
з `experiments/` не включати автоматично разом із налаштуванням CI.
`make check` перевіряє наявні пілоти, але не вимагає публікації всього корпусу.
Після першого успішного запуску додати check до наявного ruleset для
`main`. Нижче — цільові налаштування; фактичний стан наведений вище:

| Налаштування | Початкове значення |
|---|---|
| Require a pull request before merging | Увімкнути |
| Required approvals | 0, поки використовується один GitHub-акаунт |
| Required status checks | `news-library-check`, джерело GitHub Actions |
| Require branches to be up to date | Увімкнути |
| Require conversation resolution | Увімкнути |
| Do not allow bypassing the above settings | Увімкнути, включно з адміністратором |
| Allow force pushes / deletions | Залишити вимкненими |

Автор PR не може схвалити власний PR, тому обов'язкове схвалення іншим
акаунтом зараз може заблокувати роботу. Якщо з'явиться окремий рецензент
із потрібними правами, встановити 1 approval і скасування застарілих
схвалень після нових змін.

Зараз GitHub контролює обов'язковість PR; після додавання check — також CI.
Наявність якісного агентського рев'ю за
цього варіанта залишається частиною процесу. Для технічного блокування
за результатом AI-рев'ю потрібен окремий довірений check/інтеграція,
прив'язаний до фінального SHA. Сам текст звіту такого захисту не дає.

Джерела: [захист гілок](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches),
[правила схвалення PR](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews).
