# Послідовність реалізації

Почати з M1. Розробник може самостійно приймати зворотні технічні рішення
в межах [вимог](REQUIREMENTS.md) і [HLD](HLD.md). Основні продуктові та
архітектурні рішення вже погоджено; повторне опитування про них не потрібне.

## M1 — збереження, черга, доступний текст і FTS

Статус: реалізовано. SQLite/FTS та черга — `internal/library/store.go`;
адаптери/worker/UI — `internal/library/{source,worker,web}.go`. Приймання
та залишки вимог наступних етапів — TRACEABILITY.

1. Ініціалізувати Go-модуль відповідно до репозиторію. Вибрати підтримувані
   залежності SQLite/витягування тексту; додати міграції й конфігурацію.
2. Створити один сервер із простим UI: додавання URL, список, картка, стан.
3. Реалізувати транзакційне прийняття URL, дедуплікацію, стійку чергу,
   lease/retry та збереження snapshots. Додати адаптери статей і субтитрів.
4. Додати збереження/відкладання, невід'ємні цілі оцінки з історією та
   показаними версіями; кнопки `0/1/2` не обмежують введення інших значень.
   Додати теги, read/unread, FTS, ручний текст і retry для needs_input;
   фільтри й сортування — за REQUIREMENTS.
5. Додати робочі `make build`, `make test`, команду запуску й опис конфігурації.

**Готово, коли:** URL переживає перезапуск, дубль не запускає другу
обробку, текст читається без джерела, зміна оцінки лишає історію,
збережене знаходиться через FTS. Недоступний текст має явний стан.
FR-01–04, FR-09–11, FR-15–18, FR-20; ручні оцінки з FR-07.
ШІ не є залежністю цього етапу. Повне зіставлення —
[TRACEABILITY.md](TRACEABILITY.md).

## M2 — правила, дайджест, модельний прогноз

Статус: основний цикл реалізовано. Є версійні правила з поясненнями,
відсів без ШІ, явний override, cloud дайджест і optional прогноз за явно
заданим поточним профілем, Confidence search/sort, незалежний feedback,
версійна регенерація та історія. `.env`, файлове сховище й спільний
HTTP-кеш також працюють. Bounded chunking довгих текстів із checkpoints і budgeted HTTP cache
cleanup реалізовані. OpenRouter free fallback залишається запланованим; без ключа резерв неактивний.
Conditional upstream revalidation через ETag/Last-Modified реалізована.

1. Правила з версіями, внесками та порогом; порожній набір типово
   пропускає всі записи. Ручне повернення відсіяного до обробки.
2. Ollama cloud adapter, валідована відповідь, збереження результату,
   діагностика помилок. Налаштовуваний free-only резерв OpenRouter.
3. Картка з дайджестом, коротким Reasoning, окремим Confidence,
   сортуванням і фільтрами. Не змішувати це з людською оцінкою.
4. Окремий відгук про якість дайджесту; перевірка походження результатів.

**Готово, коли:** перший погоджений цикл URL → текст/дайджест → оцінка →
бібліотека → пошук працює. Відсіяний запис не викликає генерацію чи
embeddings; збої cloud не гублять даних; прогнози не змінюють людських
рішень. FR-05–08, повторна перевірка FR-10–11, FR-15–16, FR-18.

## M3 — пошук за змістом і агентське читання

Статус: реалізовано. Локальна bge-m3, стійка окрема черга й відновлювані
фрагменти з версіями моделі/джерела, cosine і RRF hybrid, фільтри, UI,
read-only API та короткий збережений контекст. Explicit rebuild відновлює
похідні індекси; FTS доступний при збої embeddings. ANN-оптимізація для
значно більших колекцій залишена майбутнім розширенням.

Chunks із джерелами, `bge-m3`, vector-пошук, поєднання з FTS, фільтри.
Read API: пошук, повний запис, фрагмент, короткий контекст. Перевірити
можливість знайти відкладене за описом задачі та відмову запису з
агентськими обліковими даними. FR-11–12, FR-18–19. Наявні тексти дозволяють
відновити індекси; відсутні embeddings не приховують записи з FTS.

## M4 — Telegram та експлуатація

Статус: код і offline приймання реалізовано. Є backup/verify/restore із primary
files, checkpoints, history/queue та paused restore. Telegram має frozen preview,
manual send/partial retry, sent/failed/unknown/restart recovery і Kyiv daily slots
із no-catchup. User обрав09:00/до5; real bot token/chat ID ще треба налаштувати
в private .env перед enable. Реальні повідомлення агент не надсилав.

Попередній перегляд і доставка на вимогу; розклад із конфігурації.
Стани доставки й неоднозначних результатів; політика повторів і
пропущених випусків. Backup/restore, контроль черги та зрозумілі помилки.
FR-13–14. Доступ з телефона до локального сайту не є умовою читання
Telegram-добірки: повідомлення має бути корисним самостійно.

## Перевірки реалізації

- Паралельне додавання дубля, перезапуск на межах транзакції/черги,
  прострочення lease й ідемпотентне збереження результату.
- Fixture-сервер для статей: redirect, timeout, завеликий/частковий текст;
  fixture субтитрів і явна відсутність субтитрів.
- Stub моделі рахує виклики: ранній reject дає 0. Неправильний JSON,
  rate limit і недоступність обох маршрутів мають визначені стани.
- Історія оцінок не змінюється після переіндексації або нового дайджесту.
- Read API дозволяє тільки читання; джерело не може підставити виконуваний
  HTML/інструкції; fetch не обходить обмеження адрес через redirect.
- Тест відновлення backup в інший каталог; доставка зі станом unknown
  не вдає гарантованої exactly-once семантики.

Живі виклики хмарних моделей не запускати у звичайних тестах.
Невеликі smoke-перевірки інтеграцій виконувати явно, збережено й відтворювано.

## Параметри, які не блокують M1

| Питання | Початковий підхід / коли визначити |
|---|---|
| Набір правил і поріг | Порожній набір до ручного налаштування на M2 |
| Основна модель | Налаштовувана; GPT-OSS — технічний кандидат з пілота |
| OpenRouter key | Без ключа резерв неактивний; не просити його в чаті |
| Telegram destination, час, розмір | Час09:00 Europe/Kyiv, до5 погоджено; token/chat ID налаштувати приватно перед enable |
| Розмір контрольної вибірки | Визначити після появи поточних реакцій користувача |
| Спосіб встановлення/автозапуску | Конкретизувати після робочого запуску M1 |

Не блокувати старт на точній імітації особистої користі, семантичній
ентропії або консиліумі. Наступні дослідницькі кроки — пояснення через
конкретні фрагменти та новизна щодо бібліотеки — виконувати окремо від
завдання надійно зберігати, знаходити й отримувати поточний зворотний зв'язок.

## Після M4 — нотатки-зв’язкові

Перший ручний експеримент реалізовано: тематичний Markdown із frontmatter
(tags/category/questions), версії, 2–20 статей з поясненнями ролей і точними
source references, derived backlinks, пошук, експорт, read API, backup.
Заморожена wiki не змінюється/не імпортується. Приклад можна створити з
картки статті або розділу «Нотатки-зв’язкові». Перевірити з користувачем
якість структури; наступний крок — cloud-підказки спільної теми/зв’язків із
повторним використанням словника та явним модельним походженням.

Пакетне введення URL реалізовано: до 500 посилань по одному на рядок,
постійна черга, ізоляція помилок, canonical dedup, результати рядків і
повтор лише проблемних URL. Кнопка переходу до непрочитаних вхідних дає
переглядати накопичене поступово. Імпорт файлів/замороженої wiki не входить.


YouTube extraction виправлено: перебір налаштованих/інших мов і metadata-only
резерв через локальний yt-dlp, захищене caption fetching, bounded helper із
public-address proxy. Автосубтитри/переклад позначені. Відсутність однієї
доріжки не прирівнюється до відсутності субтитрів. Live smoke одного проблемного
українського відео пройшов без cloud calls/userDB writes; retry старих failed
records виконує користувач із картки після перезапуску застосунку.

Розрізнення відмов дайджесту реалізовано: typed reasons/advice/action labels,
non-auto-retry для format/config/limit/source, immutable failure history і
raw rejected responses у backup. Виправлено хибне відхилення заголовка «Факти»
та заголовків у code examples; обов’язкові секції лишаються перевіреними.
Offline перевірка captured response можлива без нової генерації. Реальна
бібліотека не змінювалася агентом; user retry після оновлення застосунку.
